# 项目开发任务：Telegram SIM/eSIM 到期与续期提醒 Bot

## 1. 项目目标

开发一个基于 Go 的 Telegram Bot，用于管理实体 SIM 卡、eSIM、号码有效期、套餐有效期、流量包有效期，并在指定日期发送到期和续期提醒。

项目采用轻量级单体架构。第一阶段只开发后端与 Bot，不实现 Mini App 前端 UI；该阶段约束保留为历史基线。当前已进入第二阶段，使用 Svelte + Vite + TypeScript 开发 Telegram Mini App，并对接本文件定义的 HTTP API 与身份认证接口。第二阶段的详细前端规范见 [`docs/MINI_APP_DEVELOPMENT.md`](MINI_APP_DEVELOPMENT.md)。

系统不依赖 AI、第三方提醒服务、外部任务调度平台或独立数据库服务器。

## 2. 技术栈与约束

### 后端

- Go，使用项目开发时稳定且受依赖支持的版本。
- Telegram Bot：`github.com/go-telegram/bot`。
- HTTP 服务：优先使用 Go 标准库 `net/http`。
- 数据库：SQLite。
- 数据库访问：`database/sql`。
- SQLite 驱动：优先评估 `modernc.org/sqlite`，采用纯 Go 实现，避免依赖 CGO。
- 数据库迁移：使用版本化 SQL migration 文件，可选用轻量迁移库。
- 配置：环境变量，提供 `.env.example` 作为配置示例；生产环境不得依赖必须存在的 `.env` 文件。
- 日志：使用 Go 标准库 `log/slog`，输出结构化日志。
- 测试：Go 标准测试框架。

### 前端预留

第一阶段不创建、不开发 Svelte 页面，不生成虚假的 Mini App UI。当前第二阶段已在 `web/` 实现 Mini App；以下技术选型与 Go/前端边界继续有效，具体页面、视觉与验收要求见专项补充。

后续前端计划使用：

- Svelte
- Vite
- TypeScript
- Telegram 官方 Mini App Web App 接口
- 原生 CSS，暂不引入大型 UI 组件库

Go 后端应能够在生产环境提供构建后的静态前端资源，但第一阶段允许关闭静态文件服务，优先完成 Bot 与 API。第一阶段未启用静态文件服务；当前生产仍由同源反向代理托管静态资源，Go 继续只提供 API。前端目录和静态资源嵌入机制可以在架构上预留，不要为了预留而创建大量空文件或无意义抽象。

### 部署

- 使用 Docker 和 Docker Compose。
- 使用多阶段 Docker 构建。
- 最终运行容器仅包含应用运行所需文件。
- SQLite 数据目录必须使用持久化卷。
- 不要求 Docker、Redis、PostgreSQL 以外的额外基础设施；本项目默认不使用 Redis 或 PostgreSQL。
- 提供健康检查、日志输出、优雅退出和数据库备份说明。

### 开发原则

1. 优先使用标准库，只有存在明确收益时才引入第三方依赖。
2. 不使用 ORM、微服务架构、消息队列或复杂依赖注入框架。
3. 不把业务逻辑直接写在 Telegram Handler 中。
4. 数据库是卡片、有效期和提醒状态的唯一事实来源。
5. 所有时间处理必须明确时区，不允许依赖容器默认时区产生隐式行为。
6. 不要只生成代码骨架；必须实现可运行、可测试的完整第一阶段功能。
7. 不要在未经验证的情况下声称构建或测试已经通过。

## 4. 核心数据模型

需要先设计数据库 schema，并使用版本化 migration 创建和升级数据库。所有记录使用稳定的主键，所有关联应有外键约束。

真正删除所需的级联与 ID 不复用由版本化迁移落实（当前为 `002` 重建）：`sims`、`periods`、`rules`、`renewals`、`jobs` 使用 `AUTOINCREMENT` 主键，已删除 ID 不再分配；关联外键由原 `RESTRICT` 调整为 `CASCADE`，以支持同一事务内不可逆删除。迁移必须可重复执行并通过外键完整性测试。

### 4.1 用户 users

至少包含：

- id：内部主键。
- telegram_user_id：Telegram 用户 ID，唯一。
- timezone：用户时区，使用 IANA 时区名称，例如 `Asia/Taipei`。
- created_at、updated_at。

第一阶段可以通过环境变量配置允许访问的 Telegram 用户 ID。首次交互时，可以按配置策略自动创建用户或拒绝未授权用户。

不要将 Telegram 用户 ID 当作所有表的主键。

### 4.2 SIM 卡 sims

至少包含：

- id
- user_id
- name：用户自定义名称。
- card_type：physical_sim 或 esim。
- operator：运营商。
- phone_number：可选。
- country_or_region：可选。
- iccid：可选，敏感信息，避免写入普通日志。
- notes：可选。
- status：active 或 archived。
- created_at、updated_at。

号码、ICCID 和备注允许为空。不得要求用户提供所有字段才能创建卡片。

### 4.3 有效期项目 validity_periods

一张卡可以拥有多个有效期项目。

至少包含：

- id
- sim_id
- period_type：number_validity、plan_validity、data_package_validity 或 custom。
- name：可选标题；创建时省略、空字符串或纯空白均接受，空白持久化为 `""`；PATCH 用 `""` 清空；不得由类型标签或默认值自动填充。
- starts_at：可选。
- expires_at：到期时刻或到期日期的规范化表示。
- date_precision：区分 date 与 datetime。
- status：active、renewed、expired 或 cancelled；实际实现采用 active、expired、cancelled 三态，续期由 cycle 与独立续期历史表达。
- created_at、updated_at。

必须正确区分：

- 号码有效期
- 套餐有效期
- 流量包有效期
- 用户自定义的其他有效期

到期日期不能直接等同于 UTC 零点。对于只精确到日期的有效期，应定义明确的业务语义，例如在用户时区的到期日结束前有效，进入下一日后才算过期。具体实现必须统一并写入文档。

同一张卡允许存在多个并行的有效期项目。

### 4.4 提醒规则 reminder_rules

至少包含：

- id
- validity_period_id
- days_before：提前多少个日历日提醒。
- reminder_time：用户时区中的每日提醒时刻。
- enabled
- created_at、updated_at。

支持同一有效期设置多条提醒规则，例如提前 30、7、3、1 天以及到期当天。

应支持关闭某条规则，而无需删除历史发送记录。

第一阶段优先支持按有效期配置规则，不强制实现复杂的周期性提醒系统。

### 4.5 续期记录 renewals

至少包含：

- id
- validity_period_id
- previous_expires_at
- renewed_at
- new_expires_at
- amount：可选。
- currency：可选。
- notes：可选。
- created_at。

每次确认续期时，更新当前有效期并创建历史记录，不能覆盖后丢失旧的有效期信息。

金额使用整数最小货币单位或其他明确的精确表示，禁止使用浮点数进行货币计算。必须同时明确币种。

### 4.6 提醒任务与发送记录

设计独立的提醒发送记录，用于：

- 确定提醒对应的有效期和规则。
- 记录计划发送时间。
- 记录实际发送时间。
- 记录状态，例如 pending、sending、sent、failed 或 cancelled。
- 记录尝试次数和最近错误摘要。
- 保证同一条规则针对同一有效期和同一到期周期不会因重复扫描而无限重复发送。

建议通过唯一约束或事务保证提醒任务的幂等创建。

数据库 schema 可以根据具体调度设计增加必要字段，但不能省略发送状态持久化和去重机制。

## 5. Telegram Bot 功能

至少实现以下命令。

### /start

- 介绍 Bot 的用途。
- 展示可用命令。
- 检查用户是否有使用权限。
- 为未来 Mini App 预留启动入口。
- 第一阶段没有 Mini App 时，提供清晰的文本操作入口。

### /help

展示所有命令、参数格式和使用示例。

### /add

创建 SIM 卡，至少支持名称和卡类型。

可以使用多步对话收集运营商、号码、地区等可选信息，也可以采用明确的参数格式。

必须提供取消当前创建流程的方法，并处理用户中途退出、超时或重新开始的情况。

不要把临时对话状态当作唯一数据存储。

### /list

列出当前用户的卡片，支持显示：

- 卡片名称
- 类型
- 运营商
- 状态
- 最近的有效期信息

结果应限制单次输出数量，并为后续分页留出空间。

### /view

根据卡片 ID 或有效期 ID 查看详情，包括相关有效期、提醒规则和续期历史。

### /edit

编辑卡片资料、有效期和提醒设置。

对于日期输入，采用明确、可校验的格式，并告知用户当前使用的时区。

### /delete

支持归档卡片或取消有效期。对有关联历史记录的对象，优先采用归档或软删除，避免误删历史数据。Bot 命令维持该语义。

Mini App 另提供已确认的不可逆真正删除：删除卡片或有效期时级联删除其关联记录（提醒规则、提醒任务、续期历史），必须二次确认。两种删除语义不得混用，接口区分见 §8。真正删除后，被删除资源的数字 ID 不得复用，避免旧 Bot 回调或过期界面命中新建的替代资源。

### /reminders

查看当前用户的待发送提醒、已发送提醒和失败提醒。

### /renew

确认某个有效期已经续期，输入新的到期日期，可选输入费用、币种和备注。

执行时应使用数据库事务完成有效期更新、续期历史写入和旧提醒任务的处理。

### /cancel

取消指定的提醒任务或当前进行中的多步交互。必须区分取消提醒规则、取消单次提醒和取消对话流程。

命令的具体参数格式可以由开发者设计，但必须保持一致并记录在 README 中。

## 6. 消息按钮和回调

到期提醒消息可包含：

- 已续期
- 稍后提醒
- 查看详情
- 打开续费链接（存在链接时）

要求：

1. 回调必须验证当前 Telegram 用户是否有权操作对应记录。
2. 回调数据应简短、可解析，不直接携带敏感资料。
3. 处理成功、失败或过期的按钮操作时，都应向 Telegram 回应回调查询。
4. 重复点击按钮必须安全，不能重复生成续期记录或重复创建提醒。
5. 如果有效期已经更新，旧提醒按钮必须检查当前状态，避免错误地覆盖新数据。
6. “已续期”操作需要明确新的有效期；若没有新日期，不允许直接猜测续期结果。

## 7. 提醒调度器

提醒调度器是本项目的关键模块。

### 7.1 调度方式

使用 Go 定时器定期扫描 SQLite 中需要创建或发送的提醒任务。

不需要使用外部 Cron 服务、Redis 或消息队列。

扫描间隔应可配置，并有合理的默认值。

### 7.2 任务生成

调度器必须根据有效期、提醒规则和用户时区，计算需要创建的提醒任务。

必须避免每次扫描都重复创建相同任务。

编辑有效期、修改规则、续期或归档时，应正确处理尚未发送的旧任务，并保留必要的历史记录。

### 7.3 发送流程

采用持久化任务状态，至少支持：

1. 任务待发送。
2. 任务进入发送处理状态。
3. 调用 Telegram API。
4. 根据返回结果更新为已发送或待重试/失败。
5. 记录尝试次数和错误摘要。

必须处理 Telegram API 临时错误、网络超时、速率限制以及进程在发送前后崩溃的情况。

需要明确一个工程限制：数据库事务无法与 Telegram 消息发送组成原子事务。因此系统应实现幂等任务创建、合理重试和发送状态恢复，并在文档中说明极端崩溃场景下可能出现重复消息或漏发风险，不能宣称实现了绝对的 exactly-once 投递。

### 7.4 重启恢复

应用启动时：

- 初始化并检查数据库。
- 执行未应用的数据库迁移。
- 恢复未完成的提醒任务。
- 处理过期的 sending 状态。
- 重新扫描尚未处理的到期提醒。
- 不因重启而清空已有数据。

对错过计划时间的任务制定明确策略。默认优先补发仍有意义的到期提醒，同时避免无限发送过期的历史通知。策略应可配置或在文档中明确。

### 7.5 时间处理

- 所有日期解析必须进行严格校验。
- 使用用户配置的 IANA 时区计算提醒时间。
- 内部时间戳统一存储为 UTC，日期精度和本地日历日期应单独保留。
- 正确处理夏令时及跨时区日期变化。
- 容器系统时区不能影响业务计算结果。
- 不得使用固定的 24 小时秒数代替所有日历日计算。
- 测试边界情况，包括午夜、到期当天、跨日和时区转换。

## 8. HTTP API

为未来的 Svelte Mini App 预留版本化 REST API，例如 `/api/v1`。

至少规划并实现：

- `GET /api/v1/me`：当前用户信息。
- `GET /api/v1/sims`：获取卡片列表。
- `POST /api/v1/sims`：创建卡片。
- `GET /api/v1/sims/{id}`：获取卡片详情。
- `PATCH /api/v1/sims/{id}`：更新卡片资料。
- `DELETE /api/v1/sims/{id}`：归档卡片（204），保留历史；恢复使用 `PATCH` 且 `status=active`。
- `POST /api/v1/sims/{id}/delete`：无查询串与请求体；真正删除卡片及其有效期、规则、提醒任务、续期历史（204，不可恢复）。
- 有效期的增删改查接口；`DELETE /api/v1/periods/{id}?expected_cycle=N` 取消有效期；`POST /api/v1/periods/{id}/delete?expected_cycle=N` 仅接受正整数周期、无请求体，真正删除该有效期及其关联记录（204，不可恢复，保留所属卡片）。
- 提醒规则的增删改查接口。
- 续期历史的查询接口。
- 确认续期的接口。
- 提醒任务列表和必要的操作接口。
- `GET /healthz`：基础健康检查。
- `GET /readyz`：检查服务是否完成初始化并能够访问数据库。

使用统一的 JSON 请求与响应格式，返回适当的 HTTP 状态码。错误响应不得泄露 SQL、Token 或内部敏感信息。

对列表接口预留分页参数，校验输入参数，并对数据进行必要的排序。

所有资源查询、修改和删除操作都必须校验资源所属用户，避免通过猜测 ID 访问其他用户数据。真正删除接口对不存在或不属于当前用户的资源统一返回 404；有效期删除缺少或非法 `expected_cycle` 返回 400，周期已过期返回 409，且不得删除任何记录。

真正删除的级联行为由数据库外键与 Service 共同保证；删除资源后数字 ID 永不复用。只读接口不得因真正删除而返回其他用户或新建替代资源的数据。

### 8.1 Telegram Mini App 鉴权

实现可独立测试的身份验证模块。

前端未来通过 Telegram Web App 提供的原始 `initData` 完成认证。

要求：

- 严格按照 Telegram 官方规范验证 HMAC 签名。
- 校验 `auth_date`，拒绝超出配置有效时间的初始化数据。
- 正确处理参数排序、编码和校验流程。
- 从验证通过的数据中取得 Telegram 用户身份。
- 对不合法、过期或缺少必要字段的请求返回 401。
- 对合法但没有权限的用户返回 403。
- 不信任前端传来的用户 ID、用户名或 `initDataUnsafe`。
- 防止日志记录 Token、原始认证数据或其他敏感信息。
- 结合短期会话或每次请求携带 `initData` 的方案进行设计，明确会话期限与重放风险。
- 如果实现服务端会话，必须使用安全的随机会话标识，正确配置 Cookie 的 HttpOnly、Secure、SameSite 等属性，并提供注销和过期机制。
- 可以额外使用环境变量设置允许访问的 Telegram 用户 ID 列表。

优先评估 `go-telegram/bot` 是否提供符合需求的 Web App 数据验证功能。若复用其实现，必须核对源码或官方文档并编写测试，不得假定该功能已经处理了所有时间有效性和重放风险。

本地联调可使用独立回环测试入口，但生产鉴权不得有测试绕过：测试入口仅存在于单独测试进程，使用每进程随机假 Bot Token 与固定测试用户签发 initData，业务请求仍经过正常签名、时效和权限校验；生产启动路径不得注册该入口。前端测试引导仅在开发模式且显式启用测试模式时可用。

Bot 命令和 Mini App API 应使用一致的用户权限模型。

## 10. Docker 与部署

提供可实际运行的 `Dockerfile` 和 `compose.yaml`。

要求：

- 多阶段构建 Go 程序。
- 如果前端暂未实现，不得要求前端构建步骤才能启动服务。
- 最终运行容器尽量使用非 root 用户。
- 正确设置 SQLite 数据目录的读写权限。
- 数据库目录使用命名卷或明确的宿主机挂载目录。
- 配置容器重启策略。
- 提供健康检查。
- 正确处理 SIGTERM 和 SIGINT，停止接收新请求，关闭 Bot 和调度器，并等待正在处理的任务结束。
- 不要在多个容器中同时运行同一个数据库文件上的多个调度器。
- SQLite 应启用合理的连接池配置和外键约束；评估 WAL 模式，并提供一致性备份说明。
- 不要在每次容器启动时删除或覆盖已有数据库。
- 提供部署、升级、备份和恢复说明。

生产部署可通过反向代理或 Cloudflare Tunnel 提供 HTTPS。不要要求直接向公网暴露 Go 应用的内部端口。

## 11. 测试要求

至少编写以下测试：

### 数据层

- 数据库迁移可重复执行。
- 外键约束生效。
- 多用户数据隔离。
- 有效期更新和续期历史事务一致。
- 真正删除的级联完整性、外键行为及被删除 ID 不复用。
- 重复创建提醒任务不会生成重复记录。

### 时间与调度

- 提前多日提醒的计算正确。
- 到期当天提醒正确。
- 日期精度与时刻精度处理正确。
- 时区与夏令时边界处理正确。
- 修改到期日期后，旧任务被正确处理。
- 重启后可以恢复未完成任务。
- 发送失败后能够重试。
- 重复回调不会产生重复续期记录。

### HTTP API 与认证

- 正常请求成功。
- 未认证请求返回 401。
- 无权访问的用户返回 403。
- 不能访问其他用户的资源。
- 真正删除对不存在/他人资源返回 404，缺少/非法 `expected_cycle` 返回 400，过期 `expected_cycle` 返回 409 且不删除数据。
- 无效、伪造或过期的 `initData` 被拒绝。
- 独立测试入口只存在于测试进程，生产进程无测试路由或身份绕过。
- 参数错误返回适当的 4xx 响应。
- 错误响应不泄露敏感信息。

### Bot

- 命令解析和参数校验。
- 未授权用户无法执行操作。
- 多步交互可以取消和恢复。
- 重复按钮点击不会重复执行危险操作。

使用 mock 或接口替身测试 Telegram API，不要求自动化测试依赖真实 Telegram 账号。需要真实 Token 的手动集成测试应单独说明。

Mini App 的本地真实业务联调使用 `./scripts/test-miniapp.sh`：UI 绑定 `127.0.0.1:5180`（`/app/`），API 绑定 `127.0.0.1:8088`，使用真实 Service/Storage、隔离的临时数据库及预置数据，不需要真实 Bot Token，不启动 Bot 轮询或提醒发送器。仅独立 `cmd/miniapp-test` 提供 `GET /__test/init-data`；前端同时满足 `DEV` 与 `VITE_MINIAPP_TEST_MODE` 才可引导测试身份。生产无测试入口或鉴权绕过；详细边界见专项补充 §6.6。

## 13. 开发执行顺序

按以下阶段实施，避免一次性生成大量未经验证的代码。

当前开发重点为第二阶段 Mini App（按专项补充实施）；下列阶段划分保留为历史基线，不表示第一阶段行为或验收标准被撤销。

### 阶段 1：工程初始化

建立 Go 项目、配置模块、日志、数据库连接、迁移和 Docker 基础结构。

验收标准：应用可以启动，数据库能够初始化，Docker 镜像能够构建。

### 阶段 2：数据模型与业务逻辑

实现 SIM 卡、有效期、提醒规则和续期记录的数据层及 Service，并完成单元测试。

验收标准：核心业务可通过自动化测试验证，不依赖 Telegram。

### 阶段 3：Telegram Bot

实现命令、权限检查、必要的多步交互、按钮回调和消息格式。

验收标准：通过 mock 测试命令和回调逻辑，能在配置真实 Token 后手动验证。

### 阶段 4：提醒调度

实现任务生成、去重、发送状态、重试和重启恢复。

验收标准：时间计算、任务幂等和异常恢复测试通过。

### 阶段 5：HTTP API 与认证

实现版本化 REST API、Telegram Mini App 身份验证、用户权限隔离和 API 测试。

验收标准：接口可通过自动化测试验证，且没有跨用户访问问题。

### 阶段 6：Docker 与文档

完善生产构建、持久化、健康检查、优雅退出、备份恢复和 README。

验收标准：在干净环境中可以按文档完成构建、部署、重启和数据恢复。

每个阶段完成后运行相关测试，并修复发现的问题，再继续下一阶段。若遇到设计歧义，先提出具体问题或记录清晰的工程假设，不要自行引入重型依赖。
